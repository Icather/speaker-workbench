# 方法

[English](METHOD.md) · [中文](METHOD.zh-CN.md)

跨录音这一层是怎么工作的、为什么这么设计、以及实测出来的局限在哪。这里的一切都能用 `tools/` 里的脚本复现。

---

## 1. 数据契约

工作台读一组刻意做得很朴素的文件。任何能吐出这些文件的管线都能接进来。

### `recordings/<名字>.m4a`（或 wav/mp3/flac/ogg/aac/opus/wma）

文件名里应当含日期 —— `20260105_140000_standup.m4a` —— 因为 `sync.py` 正是从它推导录音**编号**（`0105`；同一天的多份录音会变成 `0105a`、`0105b`……）。这个编号会出现在界面的各处和每一种导出里。

### `transcripts/<同名>.moss.srt`

普通 SRT，每一条前面加上分离器自己的说话人编号：

```
1
00:00:00,000 --> 00:00:03,520
(Speaker 1) 今天主要过三件事：场地、预算，还有报名表。
```

`(Speaker N)` 这个值会被保留、并在对照模式里显示，但它**绝不**被用作分组依据 —— 它只提供第二种意见。

### `voiceprint/_final_map.json`

```json
{ "0105|0.00": "P001", "0105|3.85": "P002", "…": "…" }
```

键是 `"<编号>|<起点秒数，两位小数>"`。这是机器给出的分组，等着人来纠正。

### `voiceprint/_groups_final.json`

界面用来排序、筛选和显示置信度的逐组统计：

| 字段 | 含义 |
|---|---|
| `段数`、`时长min` | 片段数与总说话时长 |
| `出现录音`、`各录音段数` | 这个组出现在哪几份录音里（列表里那个 `★`） |
| `同录音一致性`、`跨录音一致性` | 录音内 / 跨录音的平均余弦 —— **故意分开保留** |
| `样本` | 几条有代表性的片段（`tag`、`t`、`text`） |

### `voiceprint/_embs_all.npz`

`emb` —— 一个 `N × 192` 的 float32 CAM++ 说话人嵌入矩阵 —— 外加 `meta`，一个由 JSON 字符串 `{"tag","start","end","moss","text"}` 组成的数组，与 `emb` 逐行对齐。

没有这个文件，别的一切照常工作；你只是失去了建议名。

## 2. 为什么是两阶段聚类

在这类材料上，对嵌入向量做**一次**凝聚聚类是**不行的**。在一份 96 分钟的远场语料上实测：

- 在一个看起来合理的余弦距离上用朴素的 `complete linkage`，产生的组**彼此质心相似度高达 0.95–0.98** —— 也就是一个人被切成了 5–6 个簇。
- `centroid`、`average` 和 `ward` 都会**链式吞并**：最大的簇会把整份录音吃掉（有一例吃掉了 969 段 / 105 分钟）。
- 没有任何单一连接阈值能合并一个真实的跨录音配对，因为同一个人的两半可以停在做余弦 **0.579**，而毫不相干的人能到 **0.567**。

能活下来的配置是：

```
阶段 1  complete linkage @ 欧氏 0.90   （≈ 余弦 0.595）  → 过度切分成纯净的小簇
阶段 2  centroid linkage @ 欧氏 0.60   （≈ 余弦 0.82）   在阶段 1 的簇质心上再跑
```

阶段 1 换来了**纯净**（不吞并），阶段 2 靠比较*质心*把碎片重新接起来 —— 而那正是单段噪声被平均掉的地方。

在同一份语料上的效果：

| | 组数 | 组内一致性中位数 | 低一致性组的占比 |
|---|---:|---:|---:|
| 单阶段 | 329 | 0.64 | **26 %** |
| 两阶段 | 464 | **0.72** | **0.6 %** |

> 一个值得记住的换算：在单位归一化的向量上 `cos = 1 - d²/2`。pyannote 文档里的 `clustering.threshold = 0.7155`（欧氏）等于余弦 **0.744** —— 与这里用的 0.82 接近，这算是个有用的合理性检查，而不是巧合。

## 3. 阈值是测出来的，从不猜

`tools/calibrate.py` 在你自己的语料上算四个分布：

1. **同一个人，同一份录音** —— 把每个组的片段对半分开，让两半互相关
2. **不同的人，同一份录音** —— 一份录音内所有组的质心两两相比
3. **同一个人，跨录音** —— 每个（人，录音）一个质心，两两相关，每边至少 5 段才算
4. **不同的人，跨录音** —— 等你标了一些名字之后，用 `voices.json` 里的名字

在一份真实的 10 份录音远场语料上实测（随本项目一起抽出的那个）：

| 情形 | n | 中位数 | p95 | 最大 / 最小 |
|---|---:|---:|---:|---:|
| 同人 · 同录音 | 31 | 0.944 | — | 最小 **0.834** |
| 异人 · 同录音 | 675 | 0.444 | 0.712 | 最大 **0.822** |
| 同人 · 跨录音（两边都 ≥5 段） | — | 0.925 | — | 0.913 – 0.936 |
| 1–2 段的组（跨录音） | 42 | 0.69 | — | 最大 0.80 |

所以同录音的切点是 **0.828**，我们取 0.83。跨录音的切点定得更保守，取 0.85，因为那边的反类没有标准答案。

**这里避开的第一个陷阱：** 最初的实现对所有情况用一个阈值（0.72），结果给出 **39 条建议，无一条正确** —— 因为大多数候选组都在*同一份录音内*，而那里的相似度下限天然更高。分档，别混用。

**第二个陷阱：** 1–2 段的组能冲到 0.80，而真正的同人对从 0.913 起 —— 但极小组的*噪声*下限与正样本重叠，所以小组无论得分多高都只给"弱提示"。

## 4. 声纹库（在线登记）

`sync.py:build_enrollment()`：

1. 对你已经命名的每个组，收集它的片段（均匀采样到最多 80 段，这样一个超大的组不会压倒一切），求嵌入的平均并做 L2 归一化 → 每人一个**质心声纹**。存进 `speakers.json`，连同这个人出现在哪几份录音里。
2. 对每个尚未命名的组，算出同样的质心，与整个库比对。取最近的三个候选人，采纳第一个越过其分档的。
3. 把结果写进 `data.js` 的 `groups[g].suggest = {n, s, c, same}`，让界面显示 `💡`（高信）或 `?`（弱提示）。

一切都是与一个存下来的均值做纯余弦比较 —— 不训练、不微调、不拟合模型。生产系统也是这么做的。

## 5. 诚实的局限

| 局限 | 证据 |
|---|---|
| 单段音频几乎不携带身份信息 | 跨录音的同人：**0.579**；最相似的*异*人：**0.567** |
| 说话少的说话人无法确认 | 只有 1–2 段的人最多只能拿到弱提示 |
| 相近音色无法区分 | 管线回答的是"是不是同一个声音"，而不是"这两个相近的声音里是哪一个" |
| 内容相似 ≠ 身份相同 | 两个组都"招待并介绍过同一个人"：**0.478** |
| 96 分钟的录音里约 3.6 分钟完全没有可用语音 | 三份独立转写相互吻合；电平测量证实那是静音，不是转写丢字 |

界面就是围绕接受这些局限造的：机器提议，人来决定，一个决定一次按键，处处可撤销。

## 6. 如何用你自己的音频产出这些文件

工作台是**最后**一公里，所以这个仓库刻意不背重依赖：没有 `torch`、不下载模型，整个测试套件在 CI 上跑在光秃秃的 Node 上。

本项目所基于的那份语料，其参考提取管线是这样做的：

```
对每一份录音：
    ffmpeg  -ar 16000 -ac 1                      # 归一化
    slice   按 SRT 逐条切，保留 2–12 秒的条目      # 片段时长的甜点区
    model   iic/speech_campplus_sv_zh-cn_16k-common   （3D-Speaker，约 28 MB）
    emit    emb（N × 192）、meta（每行一个 JSON）

然后：
    阶段 1  complete linkage @ 欧氏 0.90   → 纯净的小簇
    阶段 2  centroid linkage @ 欧氏 0.60   → 合并它们的质心
    emit     _final_map.json、_groups_final.json
```

任何嵌入模型都行，只要它能为每个片段产出定长向量；CAM++ 只是一个又强又小、对中文优先的选择（ECAPA-TDNN / WeSpeaker 是可以直接替换的等价物）。

**跑 `sync.py` 之前，先校验你的产物：**

```bash
python tools/inspect_embs.py
```

它会逐个检查那四项输入，核对 `meta` 的行是否与 `emb` 对齐，而且 —— 最重要的一点 —— 检查你在 `_embs_all.npz` 和 `_final_map.json` 里的 `"<编号>|<起点>"` 键是否真的对得上。那里的对不上，是"为什么页面是空的"这类报告最常见的单一原因，因为它失败时是静默的。

`tools/make_demo.py` 是上面每一种格式的一个小而零依赖的可跑示例（它会从合成声纹写出一个真正的 `_embs_all.npz`）。
